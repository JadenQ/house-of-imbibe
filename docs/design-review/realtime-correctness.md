# 设计评审 — 实时与并发正确性

**裁定**: `fix-first`

**摘要**: 实时层设计在"决策"层面与锁定决策一致（10Hz delta + 插值 + 服务端权威 + 内存聊天 + 不落库），但在"契约"层面几乎全部缺失——协议帧格式、鉴权、加入/离开/丢帧恢复、场景归属、带宽预算都只有一句散文，而 Slice 1 的 AC 弱到可以被一个错误实现通过。五个 blocker：(1) PlayerState 无 scene 字段，与 Slice 5 的双场景直接矛盾，且两片被标为可并行，必然返工；(2) WS 升级鉴权在 PRD 与所有 AC 中完全缺席，实现者最可能加 `{type:"hello", user_id}`，等于身份可伪造（Slice 6 的 ban 也随之失效）；(3) 纯 delta + 单 broadcast 通道无 seq、无 keyframe、无 player_left、未处理 RecvError::Lagged，慢速手机客户端会永久 desync 且无自愈路径；(4) avatar_snapshot 放进每帧状态，50 人 ×300B ×10Hz ≈ 150 KB/s/客户端、整机 ~7.5 MB/s，是既定预算的 ~12 倍，€5 VPS 跑不动；(5) 移动模型只说"clamp 到可走瓦片"，`player.x = tx` 的瞬移实现能完美通过 AC，服务端权威形同虚设。另有若干 major：join 快照/订阅竞态（subscribe-then-snapshot 未规定，聊天气泡会重复或丢失）、无心跳/重连/同用户双连接语义（移动端前后台切换即触发）、Tiled collision 服务端与客户端双解析的漂移风险、装饰物件 REST 写 + WS 广播的顺序与 rev 缺失、WS 入站无限流导致单人刷屏即全房 DoS、生成 worker 在事务内 await PixelLab（5-9 分钟）会把 SQLite 单写锁攥住导致全站 SQLITE_BUSY（且 busy_timeout/WAL pragma 无人负责）、NPC 对话缺少单播通道、以及 30-50 CCU 这个头条指标完全没有测试。建议在 Slice 1 落地"协议冻结 + 载荷预算 + 50 客户端 loadtest"三件事，后续切片才能是加法而非重写。

共 20 条发现。

## BLOCKER

### PRD 0001 §Implementation Decisions > Realtime room model (L100-104: `players: Map<id, {x, y, dir, avatar_snapshot, name}>`, "One room per server (MVP)") vs Slice 5 (0006 AC #1-#2: bar interior + yard + scene transitions) and PRD `decorations` schema (L136, carries `scene`)

**问题**: PlayerState has no `scene` field and the delta snapshot has no scene scoping, yet Slice 5 adds two scenes with transitions, and decorations/npcs are already keyed by `scene`. As specced, after Slice 5 everyone is in one flat coordinate space: yard players are broadcast to bar clients at overlapping tile coords, the movement clamp has no way to know which collision grid to use, and decoration events for the yard are applied by clients rendering the bar. Slice 1 and Slice 5 are also declared parallel-safe (both blocked only by #2), so the agent building Slice 5 will have to retrofit scene into the wire protocol, room state, tick loop and clamp that Slice 1 froze — exactly the rework the slicing was meant to avoid.

**建议**: Put `scene` into the protocol in Slice 1, even with a single placeholder scene. Concretely: (a) key room state as `DashMap<SceneId, Scene>` where `Scene { tx: broadcast::Sender<Arc<str>>, players: DashMap<UserId, PlayerState>, walkable: Arc<WalkableGrid>, decorations_rev: AtomicU64 }`; (b) add `scene: String` to PlayerState and to every snapshot/delta frame; (c) add a `{type:"scene_change", scene, x, y}` server->client frame plus an inbound `{type:"enter_scene"}`; (d) Slice 1 AC: "a player in scene A never appears in scene B's delta frames" as an integration test with two WS clients. Then Slice 5 only adds a second SceneId + a real grid.

### Slice 1 0002 AC #4 (L23 "WS /ws/room: on connect the server sends a full snapshot") and PRD 0001 §Realtime room model (L102-103, inbound message list)

**问题**: WS authentication is never specified anywhere in the PRD or in any slice AC. The inbound message list has no identify/hello, so player identity must come from the session cookie on upgrade — but nothing says so, and nothing requires rejecting an unauthenticated upgrade. An agent implementing AC #4 literally will most plausibly add `{type:"hello", user_id}` or trust a query param, giving full identity spoofing (walk as anyone, chat as anyone, and after Slice 6, bypass ban). The v2 research doc does say "校验 session cookie" (L612) but that fact was dropped in the PRD, and the PRD is what the agents read. Cross-site WebSocket hijacking is also unaddressed: the research doc's CSRF note (§4 L295) covers Origin checks only for REST writes.

**建议**: Add to Slice 1 ACs: (1) `GET /ws/room` runs the tower-sessions extractor *before* `ws.on_upgrade` and returns 401 without upgrading if there is no logged-in user — `user_id` and `role` are captured from the session into the connection task and are the only identity source; no inbound message may carry a user id. (2) The upgrade handler validates the `Origin` header against `PUBLIC_BASE_URL` and rejects mismatches (403). (3) Integration tests: WS connect with no cookie → handshake fails/401; WS connect with a forged `{type:"chat"}` claiming another user id → the rebroadcast frame carries the authenticated id, not the claimed one; WS connect with a foreign Origin → 403.

### PRD 0001 §Realtime room model (L104 "broadcasts a **delta snapshot** at 10 Hz (only changed players). New connections get a full snapshot on join") + Slice 1 0002 AC #4/#7

**问题**: Pure deltas over a single `tokio::sync::broadcast` channel have no recovery path, and the spec provides none. Three concrete failure modes: (a) `broadcast::Receiver` returns `RecvError::Lagged(n)` when a slow mobile client falls behind the 256-slot buffer — the dropped frames are gone forever, and because deltas only carry *changed* players, a player who has since stopped moving is never re-sent, so that client renders a ghost at a stale position for the rest of the session; (b) there is no tick sequence number, so a client cannot even detect that it missed frames; (c) leaves/joins are not represented in the delta at all (the snapshot is only sent to the joiner), so existing clients never learn a player left → permanent ghosts. This directly undermines locked decision 1 (10Hz delta + interpolation as the mechanism that makes 30-50 CCU work).

**建议**: Specify the frame contract in the PRD and test it in Slice 1: (1) every server frame carries `{v:1, seq:u64, t_ms:u64}`; (2) the tick emits a **full keyframe every N ticks** (N=30, i.e. 3s) and deltas in between — a lagged client self-heals within 3s; (3) explicitly handle `Err(RecvError::Lagged(_))` in the send task by pushing a full snapshot down that connection's private channel rather than `break`/ignore; (4) add explicit `{type:"player_joined"}` / `{type:"player_left", id}` broadcast frames on connect/disconnect; (5) include a `moving:bool` (or `anim` state) in player entries and emit one final frame on stop, so "stopped" is not inferred from frame absence. Slice 1 integration tests: two clients, kill one socket → the other receives `player_left`; force a lag by not draining one client's socket → assert it later receives a keyframe and converges.

### PRD 0001 §Realtime room model (L102, `avatar_snapshot` inside per-frame player state) vs §Avatar dual pipeline (L91-98) and Slice 2 0003 AC #4

**问题**: Carrying `avatar_snapshot` in the per-frame state blows the bandwidth budget that decision 1 depends on. A modular snapshot is a layers JSON with base/hair+color/outfit+color plus an `equipped` list of accessory refs (UUIDs) — realistically 250-350 bytes. The research doc's sizing (L101: "50 人 × ~24 字节 ≈ 1.2 KB/frame") assumed position only. With avatars inlined: 50 players × ~300 B = ~15 KB/frame → 150 KB/s **per client** at 10Hz → ~7.5 MB/s (60 Mbit/s) egress from a €5 CX22, and 150 KB/s downstream to a phone on mobile data. That is ~12× the intended budget and will not run. The `broadcast` channel also clones the frame per subscriber, so the big payload is cloned 50×/tick. Slice 2 AC #4 says "broadcast on change" (correct), which contradicts the PRD's state model — the ambiguity will be resolved by whoever codes it first.

**建议**: Make avatars a versioned side-channel, stated in the PRD: (1) delta/keyframe player entries contain only `{id, x, y, dir, moving, avatar_rev}` — target ≤32 B/player; (2) full avatar payloads are sent only in the join snapshot and in a `{type:"avatar_changed", id, rev, avatar}` broadcast frame; (3) a client seeing an unknown `avatar_rev` requests it once via `GET /api/players/:id/avatar` (idempotent, cacheable) and renders a placeholder meanwhile. Add a Slice 1 AC: "delta frames contain no avatar payload" and a Slice 2 AC asserting the delta after `PUT /api/avatar` is an `avatar_changed` event, not an inflated player entry. Record the per-frame byte budget (≤2 KB at 50 players) in the PRD so later slices have a number to violate visibly.

### PRD 0001 §Realtime room model (L103-104: inbound `{type:"move", tx, ty}` target-tile intent; "Server clamps movement to walkable tiles") + Slice 1 0002 AC #4 ("server clamps to a walkable area")

**问题**: The movement model is under-specified in a way that makes "server-authoritative" (locked decision 1) vacuous. The intent is a *target tile*, but nothing says who integrates motion between the current tile and the target, at what speed, or with what per-step collision. An implementation that sets `player.x = tx; player.y = ty` after checking only that the destination tile is walkable fully satisfies AC #4 as written — and allows teleporting across the map and through walls, so long as the landing tile is free. There is also no bound on target distance, no server-side speed cap, and no statement of whether the server pathfinds (which would be a surprising amount of logic to discover mid-slice). Separately, PlayerState is `f32 x,y` in the research skeleton while intents are tile-granular; the mixing is unresolved.

**建议**: Replace tile-target intent with a direction/velocity intent and integrate on the server: inbound `{type:"input", dx, dy, seq}` where `(dx,dy)` is a normalized 8-way direction (or zero); each 100 ms tick the server advances the player by `speed * dt` (pin `speed` in the PRD, e.g. 4 tiles/s) and rejects any step whose destination tile is non-walkable, sliding along the blocked axis. If tile-target is kept instead, then the AC must add: target must be within 1 tile of the current position (adjacency-only), the server steps at a fixed speed and re-checks each intermediate tile, and no server-side pathfinding exists. Either way add a Slice 1 integration test: "send a move intent to a tile 20 tiles away behind a wall → the player's broadcast position advances at most `speed*dt` and never enters a blocked tile."

## MAJOR

### Slice 1 0002 AC #4/#7; PRD 0001 §Realtime room model (L104 "New connections get a full snapshot on join") and §Map & decorations (L110) and chat ring buffer (L105)

**问题**: The join path has an unavoidable snapshot/stream race that the spec does not address, and every later slice reuses this path. If a connection builds the snapshot from DashMap and *then* calls `tx.subscribe()`, any mutation in between (a move, a chat line, an admin decoration add) is lost forever — a permanent ghost/missing chair with no resync. If it subscribes first and naively forwards, the client double-applies events already in the snapshot (duplicate chat bubbles is the visible symptom, since chat is fire-and-forget and also lives in the ring buffer read at join). This is the single most reused piece of realtime plumbing in the project and it is currently one line of prose.

**建议**: Mandate the subscribe-then-snapshot pattern in Slice 1 and make later slices inherit it: (1) `let mut rx = scene.tx.subscribe();` **before** reading state; (2) build the snapshot capturing `{seq, chat_seq, decorations_rev}` under the same logical point; (3) send the snapshot; (4) then drain `rx`, discarding frames whose `seq`/`chat_seq`/`rev` is already covered by the snapshot. Give every mutable collection a monotonic counter: a `chat_seq: u64` stamped on each chat line (stored in the ring buffer, echoed in the broadcast frame) and `decorations_rev` bumped per add/remove. Slice 1 test: client A spams chat while client B joins → B's rendered log has no duplicates and no gaps.

### Slice 1 0002 (no reconnect/heartbeat AC) + PRD 0001 §Realtime room model (L100-105) + locked decision 7 (mobile-first)

**问题**: Disconnect, heartbeat and reconnect semantics are entirely absent, which is a mobile-first-specific hole. Three concrete problems: (a) a backgrounded mobile tab keeps the TCP socket half-open for minutes — the player stays in DashMap as a frozen ghost since there is no ping/pong liveness check; (b) on reconnect the same `user_id` gets a second connection while the first is still registered, and two tasks then write the same DashMap entry, producing position flapping between the stale and live socket; (c) nothing removes the player from `players` or stops the tick task, and the tick task's creation via `or_insert_with` + `tokio::spawn` is racy — two simultaneous first-connects can each spawn a 10Hz broadcaster, doubling the effective tick rate and breaking client interpolation. Mobile foreground/background cycling makes all three routine, not edge cases.

**建议**: Add Slice 1 ACs: (1) server sends WS `Ping` every 20 s and closes the connection after 2 missed `Pong`s; inbound idle timeout 60 s. (2) Player state is keyed by `user_id`; on a second connect for the same user the older connection is closed with a `session_replaced` close frame before the new one registers — assert single-entry invariant in a test that connects twice as one user and checks exactly one player appears in the snapshot. (3) On socket close: remove from `players`, broadcast `player_left`. (4) The tick task is spawned exactly once per scene under `DashMap::entry(..).or_insert_with(..)` (never `contains_key` then `insert`), and shuts down when the scene has no players; add a test that connect/disconnect/reconnect 20× leaves one tick task and zero residual players. (5) Client `net` module reconnects with exponential backoff + jitter and re-applies the fresh snapshot wholesale (unit-testable without Phaser).

### Slice 5 0006 AC #1 ("collision/walkable layers loaded by both server (movement clamp) and client (rendering)") + PRD 0001 §Map & decorations (L108-110)

**问题**: Two independent parsers of the same `.tmj` — Phaser's Tiled loader in TS and a hand-rolled parser in Rust — will diverge, and divergence in a collision grid is exactly what produces rubber-banding under client prediction. The usual divergence sources are all unaddressed: tileset `firstgid` offsets, tile flip/rotation flag bits in the high bits of the gid, infinite maps stored as chunks, multiple tile layers vs an object layer for collision, and per-tile `collides` properties vs a dedicated layer. Related and worse: decorations have no `solid` flag (PRD L136), so it is undecided whether an admin-placed chair blocks movement. If it ever does, the server's collision grid becomes dynamic while the client's is derived from a static `.tmj`, and they can never agree.

**建议**: Make the server the sole authority over walkability and stop the client from deriving it: add `GET /api/maps/:scene/collision` returning a versioned, RLE-or-bitmask walkability grid (`{w, h, rev, bits}`) that the client consumes for prediction, and have the client use the `.tmj` only for rendering. Keep one Rust parser. Additionally: (1) pin the Tiled export contract in Slice 5 (finite map, one layer literally named `collision`, no flip flags, single tileset) and fail loudly at boot if violated; (2) commit a golden fixture test asserting the parsed grid matches a checked-in expected grid, so a Tiled re-export that changes semantics fails CI; (3) decide now that MVP decorations are non-colliding and write it into the PRD's Out of Scope, or add `solid INTEGER` to `decorations` and include solids in the served grid with `rev` bumped on every add/remove.

### Slice 6 0007 AC #2 ("On decoration add/remove, the server broadcasts {decoration_added}/{decoration_removed}") + PRD 0001 §Map & decorations (L110, REST mutate / WS broadcast)

**问题**: Decoration mutation crosses two transports (REST write, WS broadcast) with no ordering discipline, so several races are open: (a) a client that fetches the decoration list over REST and then subscribes can miss an add that landed in between, or double-apply one already in its list — with no version there is no way to tell; (b) DB commit and broadcast are not atomic in either order — broadcasting before commit means a client that refetches sees nothing, and committing then crashing before broadcast leaves every online client stale forever with no repair path; (c) `broadcast::Lagged` silently drops decoration events for exactly the slow mobile clients, and unlike positions these are never re-sent because there is no periodic re-broadcast; (d) no UNIQUE constraint on `(scene, tile_x, tile_y, z_layer)`, so two admins placing simultaneously produce silently stacked duplicates; (e) delete is not specified as idempotent, so a double DELETE can broadcast two `decoration_removed` for one id.

**建议**: (1) Add a monotonic `decorations_rev` per scene; the join snapshot carries `decorations` + `rev`, and every event carries the post-mutation `rev`. Clients drop events with `rev <= local_rev` and, on detecting a gap (`rev > local_rev + 1`), refetch `GET /api/decorations?scene=` to resync — this also covers Lagged. (2) Mandate order: commit the DB transaction, then bump `rev`, then broadcast; never broadcast inside the transaction. (3) Add `UNIQUE(scene, tile_x, tile_y, z_layer)` and return 409 on conflict, or explicitly document stacking. (4) Make DELETE idempotent (204 both times, broadcast only when a row was actually deleted). (5) Slice 6 test: place a decoration while a second WS client is deliberately not draining → after it drains, assert its state matches a fresh REST fetch.

### PRD 0001 §Realtime room model (L105, chat fire-and-forget) + Slice 1 0002 AC #5; locked decision 8

**问题**: Inbound WS messages have no rate limit, size cap, or sanitization. `tower_governor` (research doc L18/L598) is HTTP middleware and does not see WS frames, so one authenticated client can push chat or move frames at socket speed. Because everything shares one `broadcast` channel, a single flooder overruns the 256-slot buffer and forces `Lagged` on *every other* client — which, per the findings above, is also what silently drops decoration events and desyncs positions. So chat spam is a whole-room denial of service, not just annoying. There is also no max chat length and no escaping decision anywhere in the PRD (the research doc mentions `ammonia`/escape at L615 but that did not survive into the PRD), and chat bubbles plus the side panel are the obvious XSS sink.

**建议**: Add Slice 1 ACs: (1) per-connection token buckets on inbound frames — chat 2/s burst 5, input 20/s, interact 5/s; over-budget frames are dropped (not queued) and repeated abuse closes the socket with a policy close code. (2) `WebSocketUpgrade::max_message_size(4 KiB)` and a chat text cap (e.g. 200 chars, rejected server-side, not just in UI). (3) Server stores/rebroadcasts chat as plain text and the client renders via `textContent` / Phaser text only — never `innerHTML`; state this in the PRD and cover it with a `net`/`game-state` unit test using a `<script>` payload. (4) Also decide chat scope now that Slice 5 adds two scenes: ring buffer per scene or global (recommend per scene, matching the bubble semantics).

### PRD 0001 §Generation async UX (L118-121) + §Further Notes lightweight mandate (L179) + Slice 3 0004 AC #3; SQLite WAL from research doc §3 (L166-170)

**问题**: SQLite has exactly one writer, and the generation worker is the one component that can hold it for minutes. Per the PixelLab research doc, generation is asynchronous with 5-9 minute end-to-end latency and requires polling. If the worker opens a transaction to mark a job `running`, then `.await`s the PixelLab call or the image post-processing inside that transaction, the write lock is held for minutes and every other write — registration, login session insert, avatar save, decoration add — fails with `SQLITE_BUSY`. Nothing in the PRD or Slice 3 forbids this. Compounding it: `busy_timeout` is never set anywhere (the research doc lists WAL / synchronous / foreign_keys at L167-169 but not `busy_timeout`; it only appears as a footnote at L655), and Slice 1 has no AC for applying pragmas at all, so the WAL setup that all of this rests on is unowned.

**建议**: (1) Slice 1 AC: pragmas applied via `SqlitePoolOptions::after_connect` on **every** pooled connection — `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000` — with a test asserting `PRAGMA journal_mode` returns `wal`. (2) Slice 3 AC: the worker uses one short transaction per state transition (`pending→running`, `running→done|failed`) and holds **no** transaction across any `.await` on network I/O; all CPU-bound image work (`image`/`imagequant`/`oxipng`) runs on `tokio::task::spawn_blocking` outside any transaction. (3) Add a guardrail to §Further Notes: the 10Hz tick and the WS handler must never touch the DB — position and chat live only in memory — plus a test that asserts zero queries execute during a 2-second idle tick window. (4) Cap `max_connections` and consider a single dedicated write connection so writers queue in-process rather than racing for the file lock.

### PRD 0001 §Testing Decisions (L157-162) + Slice 1 0002 AC #7 + PRD Solution (L28, "30-50 concurrent members")

**问题**: The headline non-functional requirement — 30-50 CCU at 10Hz on a 2 vCPU / €5 VPS — has no test, no budget, and no owner in any slice. The test plan is entirely functional-contract-based (one WS client, one move, one chat). Every bandwidth and CPU regression in Slices 2 (avatar in state), 5 (two scenes) and 6 (decoration events) is therefore invisible until production, which is precisely where a solo builder cannot debug 50 real phones.

**建议**: Add to Slice 1 a `cargo run --bin loadtest` (or `#[ignore]`d test) reusing the same harness: open N=50 authenticated WS clients, drive random movement + 1 chat/10 s for 60 s, and assert (a) zero `Lagged` events server-side, (b) p95 inter-frame interval < 150 ms, (c) mean bytes/client/s under a stated budget (recommend ≤8 KB/s), (d) steady-state RSS below a stated ceiling. Print the measured numbers so Slices 2/5/6 can re-run it as a regression gate; add "re-run loadtest, budget not exceeded" as an AC on Slices 2 and 6. Also add a hard `MAX_PLAYERS_PER_SCENE` (e.g. 60) with a clean close-code rejection — 30-50 is asserted but never enforced, and cost is O(n²) in total bytes.

### PRD 0001 §Bartender NPCs (L115, "server returns the current dialogue node") + Slice 5 0006 AC #4; research doc realtime skeleton (L143-147, send task forwards only from the broadcast receiver)

**问题**: The connection's outbound path as sketched has only one source — the broadcast receiver — but several frames are inherently unicast: the join snapshot, a post-Lagged resync, validation errors, and the NPC dialogue node (which must go only to the interacting player, not the whole room). With the current design either dialogue is broadcast to everyone (wrong, and 50× the traffic), or Slice 5 has to rebuild the connection's send task. There is also no request/response correlation on `{type:"interact", target}`, and no home for the per-player dialogue cursor (PlayerState has none), so "the current dialogue node" has no defined state.

**建议**: In Slice 1, give each connection a private `mpsc::Sender<Arc<str>>` alongside the broadcast receiver and have the send task `tokio::select!` over both; route the join snapshot and any resync through the private channel. Add `req_id` to inbound messages and echo it on unicast replies so the client can correlate. In Slice 5, store the dialogue cursor in PlayerState (`dialogue: Option<{npc_id, node_id}>`) and specify that it resets on disconnect and on walking out of proximity; add a test asserting that a second WS client observing the room receives **no** dialogue frame while the first interacts.

### Slice 6 0007 AC #4 ("POST ban (login disabled)") + Slice 1 0002 AC #2 (logout) — no interaction with the WS layer specified

**问题**: Ban and logout are specified purely as HTTP-side state changes, but identity on a WS connection is captured once at upgrade and never revalidated. A banned or logged-out user's socket therefore stays open indefinitely: they keep moving, keep chatting, and keep receiving the room stream until they voluntarily disconnect — which defeats the only moderation tool in the product. "Login disabled" is not the same as "removed from the room."

**建议**: Add to Slice 6: maintain an in-memory `revoked: DashSet<UserId>` (or check a cheap epoch counter per user); on ban and on logout, look up that user's live connections and close them with a policy close code, and have the WS inbound loop drop frames from a revoked user. Test: connect as member, ban via admin REST from a second client, assert the member's socket is closed and a `player_left` is broadcast to remaining clients. Keep the check in memory so it does not add a DB read per frame.

## MINOR

### PRD 0001 §Realtime room model (L83/L104: "clients interpolate (~100-200 ms)") + Slice 1 0002 AC #4 ("client interpolates other players ~100-200 ms")

**问题**: Two interpolation details are left to chance and both are visible on mobile. (a) At a 10 Hz tick the frame interval is exactly 100 ms, so a 100 ms interpolation buffer has zero slack — a single late frame stalls remote players. (b) Nothing says how the local player is rendered. With a server-authoritative clamp and no local prediction, the joystick has a full round-trip + 100 ms tick of input lag, which will feel broken on a phone; adding prediction + reconciliation later is a rewrite of the `game-state` module the PRD wants to keep testable and decoupled.

**建议**: Pin the numbers in the PRD: interpolation delay = 150 ms (1.5 frames), buffer clamped at 2 frames, and on buffer starvation hold the last position rather than extrapolating (extrapolation walks sprites through walls). Decide local prediction explicitly in Slice 1: predict the local player immediately from input, reconcile against the authoritative position each frame, and snap only when the divergence exceeds a threshold (e.g. 0.5 tile). Both behaviors are pure `game-state` logic and unit-testable without Phaser — add a test feeding a scripted frame sequence with a dropped frame and asserting monotone, non-teleporting output.

### Slice 1 0002 AC #4 (10 Hz tick) — implementation detail not covered by any AC; research doc §2 (L159, `tokio::time::interval`)

**问题**: `tokio::time::interval` defaults to `MissedTickBehavior::Burst`: after any stall (a blocking argon2 hash on the same worker thread, a GC-ish pause, a long DB write) the tick fires several times back-to-back to catch up. Bursting 3 frames into one millisecond is exactly the input that breaks client interpolation, and it is a one-line mistake nobody notices in a functional test.

**建议**: Specify `interval.set_missed_tick_behavior(MissedTickBehavior::Delay)` (or `Skip`) on the room tick, and have every frame carry the server `t_ms` so the client interpolates against server time rather than arrival time. Relatedly: run `argon2` verify/hash inside `tokio::task::spawn_blocking` — at m=19456/t=2 each hash is 20-40 ms of CPU, and on a 2-vCPU CX22 a login burst on the tick's worker thread stalls the whole room.

### PRD 0001 §Realtime room model (L104, "New connections get a full snapshot on join") — snapshot contents never enumerated; Slice 1 0002 AC #4

**问题**: "Full snapshot" is undefined, and four later slices each need to extend it (avatar in #3, scene + npc state in #6, decorations in #7). Without a written frame schema each slice will bolt on fields ad hoc and the client's snapshot handler becomes the place where drift accumulates. There is also no protocol version field, which matters more than usual here: one binary serves `./dist`, so after a deploy an old client can still hold an open socket against a new server and mis-parse silently.

**建议**: Write the snapshot schema into the PRD: `{v:1, type:"snapshot", seq, t_ms, you:{id,name,x,y,dir}, scene, players:[...], avatars:{id->payload}, decorations:[...], decorations_rev, chat:[{seq,from,text}], chat_seq, npcs:[...]}`. Add `v` to every frame and have the client close the socket and prompt a reload on a version mismatch. Freeze this enum in Slice 1 so Slices 2 and 5 — which the PRD runs in parallel (L194) — are additive rather than colliding on the same protocol file.

### Research doc §2 (L101, "JSON 起步够用，量化后再换 MessagePack") vs PRD 0001 — no serialization or budget statement

**问题**: The PRD never records the serialization decision or a byte budget, so "switch to MessagePack later" has no trigger condition and the per-tick JSON `String` is cloned once per subscriber (50× per frame) with no note to serialize-once.
