# 文档编写规范

> 适用范围：`docs/` 下所有文件。
> 目的：区分「已核实的事实」与「调研时的判断」，让过期结论可被发现、可被修正。

## 一、三层文档结构

| 层 | 目录 | 内容 | 时效性 |
|---|---|---|---|
| **决策层** | `docs/*.md` | 工作流、技术栈选型、最终采用方案 | 随项目演进，需版本号（v1/v2） |
| **调研层** | `docs/research/` | 横向对比、候选方案清单、当时的判断 | **会过期**，只作为决策依据的快照 |
| **事实层** | `docs/reference/` | 已核实的第三方 API 端点、参数、价格、限制 | 需标注核实日期与核实方式 |

**关键原则**：调研层的结论**不允许**被当成事实引用。任何要写进代码的接口细节，必须先落到事实层并附核实记录。

## 二、事实层强制要求

`docs/reference/` 下每个文件顶部必须有：

```markdown
> **核实日期**：YYYY-MM-DD
> **核实方式**：<具体命令或 URL，能让下一个人重跑>
> **失效条件**：<什么情况下这份文档需要重新核实>
```

正文中每条事实按可信度标注：

| 标记 | 含义 | 使用条件 |
|---|---|---|
| ✅ 已核实 | 亲自打过接口 / 读过 OpenAPI spec / 探测过响应 | 必须能给出核实命令 |
| 📄 官方声明 | 官方文档或定价页写的，但未实测 | 给出 URL |
| ⚠️ 未核实 | 二手信息、博客、他人总结 | 必须标注来源 |
| ❌ 已证伪 | 曾经写过但核实后是错的 | **保留并说明错在哪**，不要静默删除 |

❌ 条目必须保留。删掉错误结论会让同一个错误被重复犯。

## 三、调研层的时效标注

`docs/research/` 每个文件顶部：

```markdown
> **调研日期**：YYYY-MM-DD
> **状态**：现行 | 部分过期 | 已被 <文件> 取代
```

单条结论若已被事实层推翻，在原处**就地标注**而非删除：

```markdown
- **PixelLab.ai** — 未见官方 MCP
  <!-- ❌ 2026-08-01 核实：有官方 MCP，65 个工具。见 reference/pixellab-api.md -->
```

## 四、第三方 API 的记录清单

记录一个外部 API 时，以下每一项都要有明确答案（"未核实"也是答案）：

1. **Base URL 与鉴权方式** —— header 名、token 格式
2. **同步还是异步** —— 异步则记录轮询端点与典型耗时
3. **尺寸/长度/配额硬上限** —— 这是最容易在调研阶段写错的部分
4. **单次调用价格** —— 按实际参数组合列，不要只写"约 $0.01"
5. **CORS 是否允许浏览器直连** —— 以及是否**应该**直连（token 暴露风险）
6. **SDK 版本与最后更新时间** —— 过期 SDK 常指向旧版 API
7. **参数名的准确拼写** —— 调研文档里编造参数名是高频错误

## 五、修订记录

每个文件底部维护「修订记录」，一行一次改动：

```markdown
## 修订记录
- **2026-08-01**：核实 PixelLab v2 OpenAPI，纠正 MCP 工具数（7 → 65）、删除不存在的 `block_size` 参数
```

修订记录写**改了什么事实**，不写"优化了措辞"。

## 六、写作约定

- 中文正文，技术名词保留英文原文（`create-character-with-4-directions` 不译）
- 价格统一 USD，标注是否为官方 estimated
- 代码块标注语言；给出的示例参数必须来自已核实的 schema
- 外部链接用完整 URL，便于离线核实
- 表格优于长段落，但**不要用表格塞入需要解释的取舍**
