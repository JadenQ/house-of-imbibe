# House of Imbibe — UI/UX 审查报告（2026-08-13）
> 8 agent fan-out：1 设计全局流程 + 6 模块并行静态审查 + 1 综合。纯代码审查，运行时需自测。
## 整体评价
整体 UX 健康度中等偏下：架构分层扎实（net/game/protocol/scene 解耦、本地预测+服务端纠正、纯状态机），核心移动/碰撞/触控/捏脸路径设计正确，但有几个 major bug 直接破坏核心体验——远端玩家永久不可见（sheet 缓存键不一致+资源洪泛）、聊天侧栏 50 条后冻结、封禁对已登录用户无效、admin 可走网格编辑对碰撞无效、HUD 换装入口生成路径杀掉后台轮询。这些问题集中在「多模块协作的接缝处」（缓存键、长度判断、跨设备数据源、admin-DB-运行时解耦），单体模块内部逻辑基本正确。修掉这 6-8 个 major 后体验会显著提升。
## 🔴 CRITICAL（崩溃/数据安全，必修）
- [实时房间] sheetCache 键不一致致远端玩家永久不可见 + 资源无限重入（逼近崩溃）：BarScene.ts:300 用裸 hash 查 sheetCache.has()，但 line 307 存的是 `av_<hash>` 键，line 313 用裸 hash get 永远返回 undefined → sprite 永不贴图、永不 setVisible(true)；同时 preparing 完成后删除、下一帧裸 hash 仍未命中 → prepareCharacterSheet 无限重入。modular 形象每帧重建 canvas（~60次/s），generated 形象每轮重下载 4方向×3帧=12张 PNG。多人房间里有 generated 形象时浏览器将持续高频下载+canvas 创建，最终导致标签页卡死/内存耗尽。这是最接近「崩溃」的问题——不是单次 crash，而是资源洪泛导致的渐进式不可用。
- [认证] 封禁对已登录用户完全无效 + 可换名重注册绕过：current_user (lib.rs:114) 的 SELECT 只取 (id,username,is_admin)，不读 banned 列，所有非 login 端点（/api/me、/api/avatar/*、/api/admin/*）和 WS 连接都放行被封用户；admin_ban (lib.rs:1580) 只 UPDATE banned=1 不清 sessions 行，用户 30 天 cookie 依旧有效可继续移动/聊天/换装；被封 admin 的 is_admin 不变，require_admin 只查 is_admin，被封 admin 仍能访问 /api/admin/*。叠加无邮箱无 IP 门禁，被封用户可立刻换名重注册。封禁功能形同虚设，仅阻止该账号下次 login。

## 🟠 MAJOR（功能错/UX 严重阻塞）
- [形象] HUD「换装」入口走生成/文字路径会杀掉后台轮询：main.ts:82 `showAvatarCreate(avatar).then(() => location.reload())`——生成/文字分支是「提交即 resolve」(avatarCreate.ts:91,159)，resolve 触发 .then 微任务立即 location.reload() 卸载页面，刚创建的 toast 与 setTimeout 轮询被销毁。结果：经 HUD「换装」提交生成时用户永远收不到「形象生成完成」通知（只有首次登录 boot 的 await showAvatarCreate(null)+startGame 路径不 reload 才存活）。违反 CLAUDE.md「生成提交后可先入场玩、job 后台轮询、完成时通知」定稿。
- [形象] D4（generated 也允许配饰）无 UI 路径——半成品：prepareGeneratedSheet (character.ts:797) 渲染层确实画 back/front accessory overlay，但没有任何 UI 能把配饰装到 generated 形象上。avatarBuilder 的 initial 在当前形象非 modular 时传 null (avatarCreate.ts:104)；put_avatar 硬写 kind='modular' (lib.rs:341) → 在 generated 形象上用捏脸保存会把 generated 转 modular 丢失 frames；avatar_equip 路由要求真实 PNG asset_id (lib.rs:382-387)，preset:hand:sword 会 404；全仓无 api.equip 调用方。generated 用户无法经 UI 装备任何配饰。
- [形象] localStorage 覆盖服务端已持久化样式（跨设备串数据）：avatarBuilder.ts:38-50 loadModularLocal 在四色匹配时执行 `{...serverCfg, ...saved}`，让 localStorage 旧值覆盖服务端值。后端 put_avatar (lib.rs:318-338) 已完整持久化 hairStyle/topStyle/bottomStyle/shoeStyle/equipped，但文件头注释(4-7行)过时声称「后端把 config 规范化会丢弃样式字段」。手机改了发型、桌面本地仍是旧样式且颜色未变 → 桌面 loadModularLocal 用旧 localStorage 覆盖服务端新发型，显示错误发型/配饰。equipped 同理被旧本地值覆盖。
- [实时房间] 聊天侧栏在房间活跃到 50 条后冻结不刷新：room.ts:130 while(chat.length>MAX_CHAT) shift() 把 ring buffer 封顶 50，封顶后每来一条先 append 再 shift，长度恒 50。BarScene.ts:340 刷新判断 `chat.length !== lastChatLen` 在长度恒 50 时永 false → setChat 不再调用，DOM 停在第 50 条快照不更新、不滚到最新。气泡(renderBubbles 每帧从 view.bubbles 重算)不受影响，但侧栏列表冻结。
- [地图渲染] admin 可走网格编辑对碰撞完全无效——功能形同虚设：客户端 BarScene.ts:169-174 solidAt() 用硬编码 BAR_MAP.solid（TS 常量）做碰撞；服务端 BarGrid (grid.rs:48) 用 include_str! 静态 bar.json 做 clamp；两者都不读 admin_set_walkable (lib.rs:1259) 写入 DB 的 maps.walkable 表。admin 在管理台编辑可走/阻挡网格并保存后，客户端碰撞不变、服务端 clamp 不变，玩家无法走通新开的路、也无法被新阻挡格挡住。
- [管理台] 管理台/酒单打开期间键盘输入泄漏到 Phaser 致角色走动 + 表单冲突：admin.ts 表单输入(input/textarea)无 stopPropagation，Phaser 键盘监听挂在 window，在 admin 表单里打字时 WASD 同步移动场景内角色（菜单/描述/酒单名称等输入均受影响）。menu.ts 同理（已记为 minor），但 admin 因有大量表单输入字段问题更严重——用户输入「washington」时角色会持续向上走。BarScene.update 无任何 isMenuOpen/isAdminOpen 早退。

## 🟡 MINOR（瑕疵）
- [认证] cookie 缺 Secure 标志 + 服务端 session 永不过期：make_session_cookie (lib.rs:127) 无 Secure，非 TLS 部署下明文 HTTP 发送可被窃听；sessions.created_at 从未被 current_user 用于过期判断，token 被 DB 永久持有，cookie Max-Age 只让浏览器 30 天后不发，但截获 token 塞新 cookie 即永久有效。

- [认证] boot() 第二次 api.me() 无 try/catch：main.ts:103 showLogin 成功后 `me = await api.me()`，若 cookie 因禁用 cookie/代理丢 Set-Cookie 抛 401，boot Promise 未捕获 reject，屏幕停在已清空的空白态。
- [实时房间] 装饰 PNG 加载失败时每帧无限重试下载：BarScene.ts:424 loadDecTex 的 img.onerror 只 delete loading 不写 cache，下一帧 guard `!decTexCache.has && !decTexLoading.has` 又 true，重新 new Image+设 src。单个坏 asset_key 以每帧速率狂打 /api/assets/{key}。
- [实时房间] 酒单 overlay 打开期间玩家仍可走动：BarScene.ts:195 update() 无 menuOpen 早退，WASD/方向键照常推进本地预测移动，玩家读菜单时可能走离吧台。移动端摇杆同理。
- [实时房间] 时钟偏移未扣单程延迟：room.ts:147 clockOffset = m.t - localMs 假设 ping 发出时刻与服务器同钟（零延迟），远程部署时 tRender 偏前，远端玩家可能多停在末帧 ~RTT/2。气泡不受影响（line.ts 纯客户端 performance.now 戳）。
- [实时房间] scene_changed / kicked 消息被 default 吞掉：room.ts:161 注释明示未实现。scene_changed 到达时客户端状态不变、Phaser 不切场景；kicked 到达时无 UI 提示也无断连重定向。
- [形象/生成中心] done job 的「应用」按钮一律 location.reload()：avatarCreate.ts:365-394 每个 done job 都渲染「应用」按钮，但 reload 始终加载最新 avatar（后端每次生成覆盖 config_json），点旧 done（已标「已被覆盖」）的「应用」实际应用的是最新而非所选 job，误导用户。
- [地图渲染] admin 重新生成背景后已连接客户端不自动刷新：无 WS map_updated 消息，已在线的玩家需手动 reload 页面才能看到新背景图；admin 端 pollMapJob 固定 120×2s=4min 超时，若背景生成超 4min 会误报「生成超时」(admin.ts:432)。

## 各模块详细 issues

### 认证流（注册/登录/登出/管理员密钥/会话/权限）（7 issues）
> 逐条核对结果——以下均正确，无问题：(1) 管理员密钥制逻辑正确：填 \"i am jaden\"→admin；不填→普通（首用户除外）；填错→普通（首用户除外）；首用户 fallback=users 表空时首注册必为 admin（INSERT...SELECT 的 (SELECT COUNT(*) FROM users)=0 分支，SQLite 单语句原子，无双注册竞态）。(2) 登录模式不显示密钥字段：login.ts 默认 mode=login，admin label/input 内联 display:none，syncAdminField 仅在 register 模式显示；toggle 切换正确显隐并清错误。(3) 会话 cookie 跨刷新/跨重启正常：token 存 sessions 表（DB 为真相源），cookie Max-Age=2592000=30天，HttpOnly+SameSite=Lax；登出 logout 删 sessions 行 + Max-Age=0 清 cookie，前端 reload 回登录。(4) 权限正确：所有 /api/admin/* 经 require_admin，未登录→401、非 admin→403；HUD「管理」按钮 index.html 内联 display:none，仅 main.ts 在 me.is_admin 时设 display='' 显示，非 admin 看不到且 API 双重拦截。(5) 注册重复用户名→409：users.username 有 UNIQUE COLLATE NOCASE（0001_init.sql），INSERT 失败→409；密码 6-128 校验在 validate_credentials 中、且在 DB 写入前返回 400。(6) 交互基本到位：登录失败显示后端 error 文案（invalid credentials，不泄露用户是否存在）；Enter 提交绑到所有 input；li-user 自动 focus；admin 字段 type=password 隐藏。(7) 渲染：.panel max-width:92vw/max-height:88vh/overflow:auto，viewport user-scalable=no，input 继承 16px（移动端不触发 iOS 聚焦缩放），横屏可用。web/src/ui/login.ts 本身无功能/交互/渲染缺陷，问题集中在后端 lib.rs 的 banned/ADMIN_KEY/session 处理与 main.ts 的容错。
- **[major/功能] src/lib.rs** 封禁对已登录用户完全无效。banned 只在 login(lib.rs:215) 检查，而所有其他端点（/api/me、/api/avatar/*、/api/admin/*）和 WS 连接都经 current_user(lib.rs:114) 鉴权，该函数 SELECT 只取 (id, username, is_admin)，根本不读 banned 列。同时 admin_ban(lib.rs:1580) 只做 UPDATE users SET banned=1，不清除该用户的 sessions 行。结果：被封用户现有 cookie（Max-Age=2592000=30天）依旧有效，可继续移动/聊天/换装；被封的 admin 甚至仍能访问 /api/admin/*（require_admin 只查 is_admin，ban 不清 is_admin）。ws_room(session.rs:24) 同样用 current_user，所以 WS 也放行。封禁仅在用户下次重新 login 时才生效。
  修复: 两处一起改：① current_user 的 SELECT 加上 u.banned，banned=1 时返回 None（视为未登录，端点返回 401）；② admin_ban/admin_demote 里追加 DELETE FROM sessions WHERE user_id = ? 立即作废旧会话，并可选 rt.leave 踢掉在线 WS 连接。
- **[major/功能] src/lib.rs** lib.rs:79 注释写「部署时可改环境变量 ADMIN_KEY 覆盖」，但 lib.rs:81 是 const ADMIN_KEY: &str = "i am jaden" 编译期常量，全代码库（含 main.rs）无任何 std::env::var("ADMIN_KEY") 查找。即环境变量覆盖根本未实现，admin 密钥写死在源码里，任何能读到仓库的人都能注册成 admin，且不重新编译无法轮换。
  修复: 在 AppState 构造时读取 std::env::var("ADMIN_KEY").unwrap_or_else(|_| "i am jaden".into())，存到 AppState 字段，register 里改用该字段而非 const；或至少把 const 改为运行期 lazy 读取 env。
- **[minor/功能] src/lib.rs** make_session_cookie(lib.rs:127) 设了 HttpOnly/SameSite=Lax/Max-Age=2592000，但缺 Secure 标志，cookie 会经明文 HTTP 发送，非 TLS 部署下可被窃听劫持。另外 sessions.created_at 从未被 current_user 用于过期判断，服务端会话永不过期：cookie 的 Max-Age 只让浏览器 30 天后不再发送，但只要 token 被截获并手动塞进新 cookie，该 token 在 DB 里永久有效。
  修复: 部署在 TLS 后时 cookie 串追加 Secure；current_user 的查询加 WHERE s.created_at > ? 绑定 now_ts()-2592000，对超 30 天的 session 视为失效（并可选清理）。
- **[minor/功能] src/lib.rs** register 的 INSERT 错误处理 `Err(_) => return Err(ApiError(CONFLICT, "username taken"))` 把一切 sqlx 错误都当作用户名冲突。UNIQUE 违例确实是 409，但磁盘满/DB locked/连接失败等也会被误报成「username taken」(409)，掩盖真实故障，用户无法理解为何注册失败。
  修复: 匹配 sqlx::Error::Database 并检查 SQLite UNIQUE 违例码(SQLITE_CONSTRAINT_UNIQUE)才返回 409；其余错误走 From<sqlx::Error> 返回 500。
- **[minor/功能] src/lib.rs** validate_credentials 用 u.len()（字节长度）做 2-20 范围，但错误信息写「2-20 chars [a-z0-9_-]」；且 is_alphanumeric() 是 Unicode 感知的，接受中文/希腊字母等。于是「酒吧」这类用户名能过校验，与信息里的 ASCII 限制不符；叠加 users.username 的 COLLATE NOCASE 只小写 ASCII，非 ASCII 不归一，可注册「alice」与「Αlice」(希腊 Alpha) 两个视觉近似账号，存在仿冒风险。
  修复: 若意图是 ASCII，把校验改成 c.is_ascii_alphanumeric() || c=='_'||c=='-' 并用 .len()（ASCII 下字节=字符）；若允许 Unicode，则改用 .chars().count() 并修正错误信息。
- **[minor/交互] web/src/main.ts** boot() 在 showLogin() 成功后执行 me = await api.me()，无 try/catch。showLogin 成功时已 ui.innerHTML="" 清空表单。若会话 cookie 因任何原因未被浏览器接受（禁用 cookie / 代理丢 Set-Cookie / 瞬时错误），api.me() 抛 401，boot 的 Promise 未捕获 reject，屏幕停留在已清空的空白态，没有错误提示也没有回到登录表单的路径。
  修复: 把第二次 api.me() 包进 try/catch，失败时重新 showLogin() 并显示「登录后未能建立会话，请重试」之类错误。
- **[minor/功能] src/lib.rs** admin_ban 只封一个 user 行，但注册无邮箱/无 IP 门禁（CLAUDE.md 明确 username+password 无邮箱）。被封用户可立刻换用户名重新注册并登录，封禁形同虚设。这是 no-email 设计的固有局限，但直接影响封禁功能的实际效力。
  修复: 无邮箱下无法根治；可在注册加同 IP 限频 / 记录注册 IP 供 admin 审计，或在文档/UI 标注封禁仅阻止该账号再次登录。

  修复: 在 BarScene.shutdown 或 main.ts 的退出路径调用 this.touch?.destroy(); 并在 destroy() 里 removeEventListener(window,'pointerdown',onFirstTouchPointer)——需把 onFirstTouchPointer 提到作用域可引用处(目前是闭包内 const, destroy 无法触达, 应存到外部变量或用 AbortController 统一管理监听器)。
- **[minor/交互] web/src/ui/touch.ts** 现象: 若 base.setPointerCapture 偶发抛错(代码 try/catch 静默吞掉, 行108-110), 则后续 pointermove 仅在手指位于 base 元素上方时才触发(base.addEventListener('pointermove',…)), 手指滑出 base 后 move 事件不再送达 → 摇杆冻结在最后位置, 直到手指滑回 base 才恢复, 造成拖拽中断。根因: 无 window/document 级 pointermove 兜底, 完全依赖 setPointerCapture 成功。
  修复: 改为在 pointerdown 时把 move/up 监听挂到 window(或用 setPointerCapture 成功则保留 capture, 失败则 fallback 到 window 监听); 或无论如何都在 window 上监听 pointermove 并按 stickPointer 过滤, 这样不依赖 capture 也能全程跟踪。
- **[minor/交互] web/src/game-state/joystick.ts** 现象: 摇杆轻推刚越过死区边界时, 速度从 0 直接跳到 0.25×42≈10.5px/s, 有可察觉的起步顿挫。根因: applyDeadZone 是硬门(mag<deadZone→0, 否则原值不重缩放), 死区边界处速度不连续(虽注释称 10.5px/s 肉眼不可见, 但起步瞬间仍有跳变, 且 analog 控制应有的"轻推慢走"在 [0,0.25) 区间完全丢失)。
  修复: 改用径向重缩放死区: mag>=deadZone 时 magnitude=(mag-deadZone)/(1-deadZone), 再按原方向重缩放 x,y, 使 [0,1] 平滑映射且 0 处真为 0, 消除跳变并恢复轻推慢走的模拟量手感。
